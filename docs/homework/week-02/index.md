## 一、项目选题

### 1.1 最终选题

**项目名称：萌宠诊所 · 宠物医院管理系统**

一句话概括：把"预约 → 接诊 → 病历 → 处方 → 收费"这条宠物就诊的完整业务链搬到线上，服务宠物主人、医生和管理员三类角色，所有数据可查、可追、可统计。

### 1.2 候选方向对比与确定过程

选题时我把候选方向按"业务背景真实度、用户角色丰富度、模块边界清晰度、后续演进空间"四个维度做了对比：

| 候选题目 | 业务背景 | 角色数 | 模块边界 | 演进空间 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 宠物医院系统 | 强，预约难/病历纸质化/收费不透明都是真实痛点 | 3 类，职责分明 | 预约/病历/收费/库存天然独立 | 认证、拆分、消息、事务都有落点 | ✅ **选定** |
| 二手交易系统 | 强，但交易+聊天+评价业务面较宽 | 2-3 类 | 聊天模块技术偏门，与课程主线关联弱 | 合理，但聊天实时通信分散精力 | 备选 |
| 图书借阅系统 | 中等，借阅/罚款流程略简单 | 2 类 | 清晰 | 模块少，拆微服务时"料"不够 | 排除 |
| 购物系统 | 强，但与课堂电商类示例重合度高 | 3 类 | 清晰 | 合理 | 排除（避免雷同） |

**确定理由**：宠物医院既有真实、人人都懂的业务背景，又天然包含三类差异化角色和五个边界清晰的业务模块。特别是"同一时段号源不能超卖""处方出库与收费入账必须一致"这类业务规则，为后续课程中的并发控制、消息队列和分布式事务提供了现成的练习场景，非常适合作为整个学期持续演进的项目。

### 1.3 项目初步边界

- **做**：单家诊所内部的宠物档案、预约、病历、收费、药品库存与基础管理。
- **不做**：多门店连锁、线上药品电商、保险对接、社区社交功能（理由见 README 3.2 节）。

### 2.2 后续计划（按课程主题安排）

| 阶段 | 计划内容 |
| --- | --- |
| 第 3-4 周 | 需求细化与数据库设计：核心实体（宠物、主人、医生、预约、病历、账单、药品）的表结构设计 |
| 第 5-6 周 | 单体实现：搭建 Spring Boot 单体工程，先跑通"预约 → 病历 → 收费"主流程 |
| 第 7 周 | 数据库持久化：接入真实数据库，完成核心模块的 CRUD 与关联查询 |
| 第 8 周 | 认证授权：登录鉴权，主人/医生/管理员基于角色的接口权限（RBAC） |
| 第 9-10 周 | 服务拆分：按模块边界拆出预约、病历、收费、库存等微服务，引入服务注册与网关 |
| 第 11 周 | 消息与事务：预约提醒、库存预警异步化；处方出库与收费入账的最终一致性 |
| 第 12 周 | 监控与部署：接口监控与日志聚合，Docker Compose 一键部署，完善文档 |

### 2.3 风险与应对

- **范围蔓延风险**：功能规划已明确"暂不实现"清单，后续每周只围绕主流程加深度，不加广度。
- **拆分时机风险**：坚持"先把单体做对、再拆"的顺序，拆分前保证模块间只通过接口交互，为拆分预留边界。
